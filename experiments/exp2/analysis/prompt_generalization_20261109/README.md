## Промахи: не все являются логической ошибкой

- **Семантически обоснованные относительно каталога:** service_navigation для прямых ссылок #24/28; metrics для вовлечённости #44/46; meetings для создания #71/72; HRP для чужих/групповых 360 #108/113. Они не согласуются с принудительной сценарной политикой.
- **Настоящие смешения предметной области:** Luna stage 2 #54 выбирает agentic_skills для обычной ML-экспертизы; #79 выбирает team_profile для возрастных рыночных бенчмарков. Формальная агентная компетенция не равна ML-навыку, а хобби/теги не равны возрастной демографии. Сам внешний источник бенчмарков у HRP также не подтверждён.
- **Уточнение применяется слишком широко:** Jev #29 «Хочу уволиться, куда перейти?» отдаётся grill при достаточно ясной навигационной цели. #49 имеет понятный причинный вопрос, хотя методика/данные влияния хобби на эффективность не определены; ни простой tag profile, ни автоматическое уточнение не гарантируют решение.
- **Недостаточный/повреждённый контекст:** #4 содержит «достиг уровня  и», без значения и AI-контекста; #135 не обозначает внешний рынок/ТОП-600; #190 не обозначает сегмент пользователя. Попадание в единственную метку может требовать домыслить отсутствующий контекст.
- **Пограничный смысл:** #114 «Что изучить … для развития длинного взгляда» допускает материалы (mcp_internet) или выбор навыка/трек (ai-coach). #112 «профиль моей роли» подходит политике ai-coach, но отдельная операция получения такого профиля недостаточно описана.
- **Покрытие каталога:** #78 просит придумать вопросы для встречи со студентами. Результат понятен, однако ни HRP, ни grill не являются очевидным владельцем по описанным операциям. Вызов с фиксированным Choice всё равно вынужден выбрать кого-то; отдельного варианта «нет подходящего» нет.

## Насколько это leak

**Прямая передача эталона отдельного примера:** не обнаружена. **Использование тестовой разметки при проектировании промпта:** присутствует. Автор этой политики просмотрел ошибки и эталоны всех 193 запросов, затем записал специальные соответствия, включая противоречия каталогу и значения по умолчанию для неоднозначных вопросов. Это test-informed prompt fitting и семантическая утечка правил меток. Отсутствие few-shot списка точных вопросов не делает такую оценку независимой.

Наиболее переносимая часть: действие важнее тематического слова, конкретная компетенция важнее общего слова «аналитика», поиск материала отличается от статуса курса, существующее назначение — от подбора нового. Наиболее рискованная: «вопреки описанию выбирай X», добавление отсутствующей компетенции и восстановление скрытого контекста из знакомого вопроса.

Бизнес-правило в системном промпте само по себе допустимо. Если владельцы production подтвердили его независимо от этой корзины и исполнитель действительно поддерживает операцию, это легитимная конфигурация роутера. В текущем опыте таких подтверждений нет: правила сформированы после просмотра gold. Поэтому 91–94% — качество согласования с этой размеченной корзиной и политикой, а не оценка production success.

Повторный выбор метода по отклику теста создаёт зависимость от тестовых данных; это общий риск адаптивной оценки ([Google Research](https://research.google/blog/the-reusable-holdout-preserving-validity-in-adaptive-data-analysis/)). Отделение данных для выбора системы от финальной проверки описано также в [документации scikit-learn](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage). Здесь выбор промпта играет роль настройки системы, даже без изменения весов модели.

## Перенос на production и другие наборы агентов

Количественно предсказать production accuracy из этих запусков нельзя. Правила могут переноситься на новые формулировки тех же подтверждённых бизнес-сценариев, но отдельная проверка необходима. Перенос на новый каталог особенно сомнителен, поскольку сценарный текст содержит фиксированные имена и переопределения их возможностей.

1. Считать текущие 193 запроса development/regression-набором: их уже все использовали для настройки. Разбить их задним числом недостаточно для независимого теста этого промпта.
2. До просмотра нового теста зафиксировать промпт, каталог и подтверждённые бизнес-исключения. Gold назначать по реальным возможностям и согласованному владельцу; допустимые альтернативы разрешать только при проверенном пересечении, не вслед за ответом модели.
3. Собрать новый набор из реальных обращений/независимых авторов: положительные примеры всех 17 агентов, похожие намерения с разными действиями, короткие запросы с и без нужного контекста, многопредметные и неподдерживаемые запросы. Не ограничиваться перефразированием этих 193.
4. Разделять семейства сценариев/источники, а не случайные почти одинаковые строки. Для переноса на другие routing-системы включить другой каталог, переименование/перестановку кандидатов, новые пересекающиеся специализации. Это план проверки, таких прогонов пока нет.
5. Считать top-1, macro recall и ошибки по агентам; отдельно технические отказы и unsupported-вопросы. Для production дополнительно проверять успех исполнения после маршрута: один routing-hit его не доказывает.

## Новый общий промпт

[RU](../../../../exp2/prompts/routing_general_ru_exp2.txt) и [EN](../../../../exp2/prompts/routing_general_en_exp2.txt) не содержат имён агентов, списков эталонных сценариев, произвольных defaults для «моих оценок»/«пересечений» и приоритета над противоречащими возможностями. Они задают сопоставление действия, данных, результата и ограничений. Краткое описание уточняется полным документом. Инструкций о выводе текста, инструментах и расчёте confidence нет.

Это **менее подогнанный кандидат**, а не доказанно чистый/лучший промпт: он также создан после знакомства с корзиной. На старом gold score может снизиться, особенно там, где gold конфликтует с каталогом. Ни величина снижения, ни рост production качества не измерены. Исторический сценарный default оставлен для воспроизводимости; общий выбирается через --system-prompt. Реальных вызовов моделей в ходе этого анализа не выполнялось.
